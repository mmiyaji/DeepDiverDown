# Arrow IPC：ストリーム形式とファイル形式の違い

## 1. 題材と範囲

Arrow IPC の 2 つの形式を、バイト列の並びと読み取りの経路で比べる。2026 年 11 月時点の公式ドキュメントに基づく。レコードバッチの内部（バッファの配置）、Flight は扱わない。

## 2. 共通のメッセージ列

ストリーム形式の本体は、カプセル化したメッセージの列である。Schema が先頭で、辞書バッチ、レコードバッチが続く。各メッセージは継続マーカー 0xFFFFFFFF、メタデータ長（32 ビット）、Flatbuffers の Message、パディング、本体の順に並び、全体を 8 バイトの倍数にそろえる。ファイル形式の中央部は、この列と終端マーカーをそのまま置く。

## 3. 終端

ストリームは、0xFFFFFFFF の後に長さ 0 を書いて終える。接続を閉じて終えてもよい。順次読みの読み手はこの終端か接続の終了で止まる。

## 4. ファイル形式だけの要素

| 位置 | 要素 | 役割 |
| --- | --- | --- |
| 先頭 | `ARROW1` とパディング | ファイル形式の判別。8 バイト境界にそろえる。 |
| 終端の後 | フッター | Schema の複製と、全データブロックのオフセット・サイズ。 |
| 最後 | フッター長と `ARROW1` | 読み手が末尾から最初に読む位置。 |

ファイルでは、辞書バッチをレコードバッチより前に置く必要がない。辞書の置き換え（同じ ID の非 delta を複数）は許されず、delta はフッターの順に適用する。フッターの Flatbuffers の細部は仕様の `File.fbs` にあり、ここでは確認していない。

## 5. 読み取り経路の違い

- ストリーム：`pa.ipc.open_stream()`。先頭から順に読み、バッチの順番は固定で、ランダムアクセスはない。入力は読み取りだけでよい。
- ファイル：`pa.ipc.open_file()`。末尾のフッター長でフッターを読み、`get_batch(i)` で番号指定してバッチの位置へ seek する。入力は seek できる必要がある。

したがって、後ろの 1 バッチだけを読みたい場合はファイル形式、書きながら送り続けたり、終わりが未定の入力はストリーム形式が合う。推奨の拡張子はファイルが `.arrow`、ストリームが `.arrows` である。

## 6. 実装例 AWS：EC2 上の Python と S3

EC2 上の Python が、同じ PyArrow の書き込み API でファイル形式の `.arrow` と、ストリーム形式の `.arrows` を S3 に置く構成例。公式ドキュメントの API を組み合わせた代表例で、実在の導入事例ではない。S3 に対する範囲読みの回数と速度は未検証。

## 7. 未確認の事項

- フッターの Flatbuffers 構造の細部。
- S3 での範囲読みの回数と速度。
