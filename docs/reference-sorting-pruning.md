# 読み取りの絞り込み：ソートとプルーニング

## 1. 目的と前提

このリファレンスでは、`orders` テーブルを `order_date` でパーティション化し、各パーティション内を `customer_id` の順に整理した場合に、読み取り対象がどのように絞り込まれるかを追う。ここでいう「ソート」は、書き込み時に保存データを整理する物理レイアウトと、クエリの結果を並べ替える `ORDER BY` を区別する。

題材は説明用の論理モデルであり、特定の製品や実環境のファイル数・レプリカ数・インデックスの存在を主張しない。実装によって、パーティション、ストレージブロック、データファイル、列チャンク、min/max 統計の呼び方と適用範囲は異なる。

## 2. 保存時のソートとクエリ時の ORDER BY

BigQuery のクラスタリングは、ユーザー指定のクラスタ列の値に基づいてストレージブロックを整理する。複数列では列順が優先順位になるため、このモデルでは `order_date`（パーティション境界）の内側で `customer_id` を先頭の検索列として扱う。[BigQuery クラスタテーブル](https://cloud.google.com/bigquery/docs/clustered-tables) は、保存ブロックを整理する性質と、クエリのフィルターが読むブロックを選ぶ性質を説明している。

一方、`SELECT ... ORDER BY customer_id` はそのクエリが返す行の順序を要求する演算であり、既存の保存レイアウトを作り直したり、次回以降のクエリの物理順序を保証したりする宣言ではない。したがって、保存時の整理はプルーニングの候補を作り、`ORDER BY` が必要なら残った結果に対する並べ替えとして別に考える。

## 3. パーティション・ブロックの候補を絞る

例として次の条件を考える。

```sql
SELECT order_id, customer_id, total
FROM orders
WHERE order_date >= DATE '2026-01-01'
  AND order_date <  DATE '2026-02-01'
  AND customer_id = 42;
```

BigQuery はパーティション列への適格なフィルターを使って、条件に一致するパーティションだけをスキャンし、残りを入力スキャンから除外する。定数に基づくフィルターはパーティション・プルーニングに使えるが、別テーブルの値のような動的な式では使えない場合がある。[パーティションテーブルのクエリ](https://cloud.google.com/bigquery/docs/querying-partitioned-tables) を参照。

残ったパーティションの中では、実装が保存ブロックやデータファイルの統計を利用できる。BigQuery のブロック・プルーニングではクラスタ列のフィルターとブロックメタデータから関連ブロックだけを読む。Parquet のようなファイル形式や Iceberg のようなテーブル形式でも、同様の min/max などの統計を使えるか、どの単位で使えるかは実装・ファイル生成条件に依存する。ここで「ブロック」と「ファイル」を同一視せず、抽象的な読み取り単位として表す。[BigQuery のブロック・プルーニング](https://cloud.google.com/bigquery/docs/clustered-tables) および [Iceberg のソート順](https://iceberg.apache.org/spec/#sorting) を参照。

## 4. 残ったデータを読み、必要なら並べ替える

パーティションとブロック／ファイルを除外しても、条件に一致する行が含まれる読み取り単位はスキャンする。`customer_id = 42` を満たす行だけを結果に残し、投影した列だけを読むかどうか、また読み取り単位の統計をどこまで利用するかは実装の責務である。プルーニングは一致する行を生成する処理ではなく、読む必要のない領域を先に減らす処理である。

クエリに `ORDER BY` を付けた場合、残った結果を指定順に並べる処理が追加される。保存時に `customer_id` の順序を保つ仕組みがあっても、パーティションやファイルをまたぐ結果順序が自動的に保証されるとは限らない。クエリの順序保証と保存レイアウトの最適化は、別の要件として検証する。

## 5. 実装ごとの境界

パーティション・プルーニングは、テーブルのパーティション仕様とクエリ述語を照合する最適化である。ブロック／ファイルのスキップは、保存時のソートやクラスタリングと、読み取り単位に保持された統計を照合する最適化である。どちらも適用されなければ全候補を読む可能性があり、適用されても残った領域の読み取りは必要になる。

BigQuery は `PARTITION BY` と `CLUSTER BY` を組み合わせ、パーティション内をクラスタ列で整理できる。[パーティションとクラスタの組み合わせ](https://cloud.google.com/bigquery/docs/clustered-tables#combine_clustered_and_partitioned_tables) は、この二段階の絞り込みを製品機能として説明する。Iceberg はパーティション変換とデータ／削除ファイル単位のソート順をメタデータとして宣言できるが、書き込み側が高価なソートを省略することもある。[Iceberg 仕様](https://iceberg.apache.org/spec/#sorting) を参照し、製品固有の保証を混ぜない。

## 6. シナリオで追う読み取り

### 6.1 月と顧客を指定する

1. クエリエンジンは `order_date` の定数範囲を使い、対象月以外のパーティションを候補から外す。
2. 対象パーティション内で `customer_id = 42` と保存ブロック／ファイルの統計を照合し、範囲外の読み取り単位を外す。
3. 残った単位をスキャンし、行条件を評価して結果を返す。

### 6.2 保存順序を結果順序と取り違えない

1. 書き込み側はパーティション内の `customer_id` を整理し、後続のスキップに使える局所性を作る。
2. クエリは `WHERE` で候補を絞るが、保存順序だけでは全結果の順序保証を得ない。
3. 利用者が `ORDER BY customer_id` を要求した場合、読み取った結果に順序付けを適用する。

### 6.3 述語が絞り込みに効かない場合

1. `order_date` を加工したり、別テーブルの値と比較したりして、パーティションの境界を事前に確定できない述語を使う。
2. パーティション・プルーニングが弱まり、より多くのパーティションが候補になる。
3. `customer_id` の条件が複雑な式でブロック統計と照合できない場合、ブロック／ファイルのスキップも弱まり、候補領域をスキャンしてから行を評価する。

## 7. 学習目標

- 保存時のソート／クラスタリングと、クエリの `ORDER BY` の意味を分けて説明できる。
- `order_date` のパーティション・プルーニングと `customer_id` のブロック／ファイル・スキップを、異なる最適化として追跡できる。
- 最適化後も残ったデータをスキャンし、必要なら結果を並べ替えるという実行の境界を説明できる。

## 8. 保存順序の書き直し（sort rewrite）

ランダムな順で書かれたファイルは、どのファイルも customer_id の最小値〜最大値がほぼ全範囲になり、統計で 1 つも除外できない。テーブル形式の sort rewrite（Iceberg の `rewrite_data_files` の sort 戦略、Delta Lake の Z-order など）で customer_id の順に並べ替えて書き直すと、各ファイルの範囲が狭くなり、customer_id = 42 を含むファイルだけを読めばよくなる。書き直しは読み取りとは別の保守作業で、計算とストレージ書き込みの費用がかかる。出典 [Iceberg Maintenance](https://iceberg.apache.org/docs/latest/maintenance/)
