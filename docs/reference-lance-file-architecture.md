# Lance ファイルの基本アーキテクチャ

## 1. 対象

Lance の列指向ファイル 1 つの中のバイト配置と、読み書きの流れを扱う。2026 年 11 月時点の公式仕様（lance.org の File Format）に基づく。複数ファイルをバージョン付きのテーブルとして管理する仕組み（データセット形式）は対象外で、別の層にあるとだけ記す。

## 2. ファイルの並び

ファイルは先頭から順に、データページ、列メタデータ（列ごとの protobuf）、列メタデータのオフセット表、グローバルバッファのオフセット表、固定長のフッターで構成する。フッターは列メタデータ 0 の位置、2 つのオフセット表の位置、グローバルバッファ数、列数、メジャー・マイナーのバージョン、マジック `LANC` を持つ。値はすべてリトルエンディアンである。バッファは絶対オフセットで参照するため、連続して置く必要はない。バッファは 64 バイトに整列し、ダイレクト I/O 向けには 4096 バイトの整列が要る。

## 3. ページと列メタデータ

ページは 1 つの列の行を持ち、列ごとにページ数は異なる。ページのメタデータは `buffer_offsets`、`buffer_sizes`、行数 `length`、`encoding`、先頭行の行番号を示す `priority` を持つ。トップレベルの行はページをまたがない。Parquet のような行グループはなく、行の境界で任意にファイルを分割できる。推奨のページサイズは 8 MB で、クラウドストレージで独立した 1 回の I/O に見合う大きさとして選ばれている。

## 4. エンコーディング

コンテナはエンコーディングを知らず、各ページが自己記述的な protobuf でエンコーディングを持つ。未知のエンコーディングは読み誤らず、非対応として報告できる。列やページごとに異なるエンコーディングを使える。既定の構造エンコーディングは、小さな値向けの mini-block、約 256 バイトを超える値向けの full-zip、単一値の constant である。圧縮にはビットパッキング、FSST、辞書、RLE、zstd、lz4 などがある。詳細は仕組み図「ページ構造とランダムアクセス」で追う。

## 5. グローバルバッファと外部バッファ

グローバルバッファにはスキーマ、ファイルのインデックス、列統計などを置ける。統計の形式は File Format の仕様に定義がなく、未確認である。1 ページに数行しか入らない大きな値は、外部バッファに置き、ページには位置を記録する。blob の保存方式（Blob V2 の Inline、Packed、Dedicated、External）は公式ブログの一覧で名前だけ確認した。仕様の本文は未確認である。

## 6. 読み書きとストレージ

書き込み側はデータページ、列メタデータ、オフセット表、フッターの順に書く。読み取り側はファイル末尾の 1 セクター（ローカルで 4 KiB、クラウドではより大きく）を読み、続けてメタデータの残りを読む。IOP は 1〜2 回である。メタデータのサイズを別の場所に持てば 1 回になると仕様にある。必要な列だけを読めるが、列を増やすと IOP も増える。オブジェクトストレージではファイルが 1 オブジェクトになり、範囲読み取りでページの一部を取る。

## 7. シナリオ

ファイルを書いて読む。エンジンがページを書き、列メタデータとフッターを最後に書いて保存する。読み取り側はフッターからオフセット表をたどり、列メタデータで必要なページを選んで範囲を読む。大きな値は外部バッファを読む。

## 8. 実装例：AWS の EMR on EC2 と S3

EMR on EC2 の YARN 上で Spark を動かし、Lance の Spark コネクタで S3 の Lance ファイルを読み書きする代表的な構成である。Lance のドキュメントで Spark コネクタの存在は確認したが、EMR での動作検証と対応バージョンは未確認で、実在の導入事例としては扱わない。

| 機能 | 担い手 |
| --- | --- |
| 書き込みエンジン | Spark Executor と Lance ライブラリ |
| 読み取りエンジン | Spark Executor と Lance ライブラリ |
| 位置情報のキャッシュ | Executor のメモリ内の検索キャッシュ |
| ファイルの保存先 | Amazon S3 のオブジェクト |

## 9. 未確認の事項

列統計とデータスキップの形式、Blob V2 の仕様本文、バージョンごとの互換規則は未確認である。性能の数値（ブログの「ストレージ 50% 以上削減」「blob 読み取り最大 68 倍」など）はプロジェクトの自己申告で、検証していない。
