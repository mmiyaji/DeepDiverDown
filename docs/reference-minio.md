# MinIO の概要（S3 互換 API・消失訂正・提供形態の変更）

取得日は 2026 年 11 月 28 日。

## 1. 概要と提供形態・ライセンスの現状

MinIO は S3 互換 API を持つオブジェクトストレージである。GitHub の `minio/minio` リポジトリは 2026 年 4 月 25 日にアーカイブされ、README は「このリポジトリはもう保守されていない」と述べる。コミュニティ版はソース公開のみで、新しいビルド済みバイナリは提供されず、過去のバイナリも更新されない。ライセンスは GNU AGPL v3.0、ドキュメントは CC BY 4.0 と記載されている。ソースからは Go 1.24 以降で `go install`、または Docker イメージのビルドで導入できる。

MinIO 社の後継は 2 種類で、README が案内している。AIStor Free は単一ノードのみの無料版で再配布は禁止、分散構成は対象外。AIStor Enterprise は商用の期間ライセンスで、料金は使用可能容量による。複数ノードの構成と 24 時間 365 日のサポートが含まれる（料金ページの記載。Free の容量上限は記載がなく未確認）。公式ドキュメントは AIStor の URL（`docs.min.io/enterprise/aistor-object-store/`）へ移っており、旧 `min.io/docs/minio/linux/...` は 301 で転送される。

- [MinIO GitHub リポジトリ](https://github.com/minio/minio)
- [MinIO Pricing](https://www.min.io/pricing)

## 2. 要求の流れ

S3 クライアントの要求はロードバランサーを経てノードの MinIO サーバーに届く。サーバーが認証・認可を確認し、保存先を決める。Linux 手順の概要ページは、導入、ロードバランシング、ネットワーク暗号化、サーバー側暗号化、FIPS モード（任意）を別項目として並べている。認証・認可（IAM、外部 ID プロバイダー、KES）の仕組みは今回取得した資料になく未確認。

- [MinIO AIStor Linux](https://docs.min.io/enterprise/aistor-object-store/installation/linux/)

## 3. 消失訂正セットと耐久性

以下は AIStor の資料の記述であり、アーカイブ済みのコミュニティ版に同じ内容が当てはまるかは未確認。

- サーバープール内のドライブは同数ずつの消失訂正セットにまとまる。既定のセットは 2〜16 ドライブで、AIStor の `RELEASE.2026-02-02T23-40-11Z` 以降は `MINIO_ERASURE_SET_DRIVE_COUNT` で 32 まで広げられる。セットの大きさはプールの初期化時に決まり、後から変えられない。
- 書き込みでオブジェクトをデータシャード K とパリティシャード M（N = K + M）に分割する。パリティ（EC:N）は 0 からセットの半数まで選べる。本番は EC:3 以上が必要で、5 ドライブ以下の自動既定値は開発・試験向け。16 ドライブの例の既定は EC:4。パリティを変えても既存オブジェクトは更新されない。
- 読み取りは任意の K 個のシャードがあれば成立する。書き込みは全 N 個を試み、K 個の確認で成功する。パリティがセットの半数ちょうどのときは、分断時の二重書き込みを防ぐため書き込みクォーラムが K+1 になる。
- PUT 中にオフラインのドライブがあると、1 台につきパリティが 1 増え、オブジェクトのメタデータに記録される。上限は `MINIO_ERASURE_PARITY_UPGRADE_BUDGET`（既定は障害 1 回あたりセット容量の 1%）。
- ヒーリングは、読み取りクォーラムが残る限り、データ・パリティいずれのシャードからでも欠損を再構築する。クォーラムを失うと、通常は復元できない。
- Kubernetes では spread zone でシャードをラックや可用性ゾーンに分散できる。
- ビットロット対策は取得した資料に記載がなく未確認。

- [MinIO AIStor Erasure Coding](https://docs.min.io/enterprise/aistor-object-store/operations/core-concepts/erasure-coding/)

## 4. サーバープールと拡張

ドライブはサーバープールに属し、消失訂正セットはプールごとに作られる。容量はプールの追加で広げる。拡張の構文、ファイルシステム、ポート、構成ファイルは個別手順ページを取得しておらず未確認。

## 5. 実装例：Linux 上の分散構成

| 機能 | 具体的な担い手 |
| --- | --- |
| クライアント | S3 互換 SDK や CLI を使うアプリケーション |
| 入口 | 利用者が用意するロードバランサー |
| API・認証・消失訂正・ヒーリング | 各ノードの MinIO サーバー |
| ドライブ | 各ノードのローカルドライブ |
| 拡張 | 運用担当者によるサーバープールの追加 |

利用者が自前のサーバーで MinIO、OS、ドライブを運用する構成。公式資料に基づく代表例であり、導入事例や動作検証済みの構成ではない。複数ノードの運用は AIStor Enterprise か、ソースからビルドしたコミュニティ版が前提で、AIStor Free は単一ノードのみ。ノード数、ドライブ数、パリティの値は未確認で、図には書かない。
