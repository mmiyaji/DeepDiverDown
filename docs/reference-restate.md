# Restate の概要（耐久実行・ジャーナル・サービス型・クラスタ）

2026 年 11 月時点の公式資料に基づく。確認できない点は「未確認」と書く。

## 1. 概要と耐久実行

Restate はハンドラー（業務ロジックの関数）を耐久的に実行する基盤である。Restate Server は単一の Rust バイナリとされ、サービスの前段でリバースプロキシやメッセージブローカーのように動く。呼び出しを受け、ステップ（サービス呼び出し、DB 更新、タイマーなど）とその結果をジャーナルに記録する。障害後はジャーナルを再生し、完了済みのステップを飛ばして続きから実行する。失敗したステップは指数バックオフで再試行し、方針は設定できる。呼び出し（invocation）は HTTP、Kafka、プログラムから起動でき、冪等キーで重複した要求は元の結果を返す。サーバーが状態と実行履歴を保持して要求とともに渡すため、サービスは状態を持たなくてよい。サービス側がジャーナルを返せなくなると、サーバーはその実行を止めて別のインスタンスで再試行する。SDK は TypeScript、Java、Kotlin、Python、Go、Rust、Ruby。

アーキテクチャの資料によると、パーティションごとにプロセッサーのリーダーが 1 つあり（フォロワーは任意）、有効なリーダーだけがサービスへの呼び出しを扱う。リーダーはサービスのエンドポイントへ双方向ストリームを開いて呼び出し、組み込みの RocksDB にジャーナル・冪等性のメタデータ・Virtual Object のキー別状態・タイマーの索引を持つ。この RocksDB はログから再構築できる派生物で、正の記録ではない。ワークフロー ID、Virtual Object のキー、冪等キーはハッシュでパーティションが決まり、インジェストがその時点のリーダーへ転送する。

サービスのデプロイは UI、CLI、Admin API のいずれかで登録する（CLI は `restate deployments register <URL>`）。登録すると新しいデプロイが既存のサービス定義を壊さないか検査され、ハンドラーの追加は通るが、削除や改名は `--breaking` を付けないと失敗する。新しい要求は最新のデプロイへ、進行中の要求は元のデプロイへ流れる。HTTP/1.1 しか使えない対象には `--use-http1.1` を付ける。

- [Restate Architecture](https://docs.restate.dev/references/architecture)（2026 年 11 月 28 日取得）
- [Versioning（デプロイの登録）](https://docs.restate.dev/operate/registration)（2026 年 11 月 28 日取得）

## 2. サービスの型

| 型 | 状態 | 並行性 |
| --- | --- | --- |
| Service | なし | 並列数の上限なし |
| Virtual Object | キーごとのキー値状態 | キーごとに書き込み権限のあるハンドラーは同時に 1 つ。読み取り専用の共有ハンドラーは並走できる |
| Workflow | ワークフロー ID ごとの状態 | メインの `run` ハンドラーは ID ごとに 1 回。共有ハンドラーは並走し、promise の解決や状態の参照に使う |

- [Services](https://docs.restate.dev/foundations/services)

## 3. クラスタ、ログ、スナップショット

パーティションごとに 1 本のログを持ち、ログは loglet のセグメントでできている。有効な loglet は 1 つで、書き込みは定足数で複製する。ログの複製数 n なら n-1 台までの log-server の喪失に耐える。パーティション処理の複製（フォロワー）はホットスタンバイで、耐久性は上げない。パーティション数は既定 24 で、構築後に変更できない。役割は `admin`、`http-ingress`、`log-server`、`metadata-server`、`worker`。metadata-server は n 台の障害に耐えるのに 2n+1 ノード必要。スナップショットは S3 互換の保存先が必要で、ログの切り詰め、ノードの後からの追加、パーティションの高速な引き継ぎに使う。共有ファイルシステムは対象外。オートスケーラーでの自動増減は想定されていない。

- [Clusters](https://docs.restate.dev/operate/clusters)

## 6. 実装例：自前の Linux 上のクラスタ

| 機能 | 具体的な担い手 |
| --- | --- |
| クライアント | HTTP クライアント |
| 受付・実行の進行・複製ログ・実行履歴と状態・管理 | Restate Server ノード群（worker・log-server・http-ingress・admin の役割） |
| メタデータ | metadata-server ロールのノード |
| ハンドラー | SDK を組み込んだサービスのデプロイ |
| スナップショット | S3 互換ストレージ |
| 副作用の呼び出し先 | 外部 API・DB |

利用者が自前のサーバーで Restate とサービスを運用する構成。公式資料に基づく代表例であり、導入事例や動作検証済みの構成ではない。図は 1 つのまとまりに省略しており、ノード数・複製数・認証・TLS は未確認。
