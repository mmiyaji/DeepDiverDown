# Arrow IPC（Feather V2）の基本アーキテクチャ

## 1. 題材と範囲

Apache Arrow の IPC ファイル形式（Feather V2 と同じ）を、1 つのファイルの中のバイト配置と、書き手・読み手・ストレージの関係で捉える。2026 年 11 月時点の公式ドキュメントに基づく。図は説明用で、実環境での実行や計測は行っていない。Arrow Flight は IPC のメッセージを RPC で運ぶ仕組みとして存在するが、この図では扱わない。

## 2. ファイルの構成要素

IPC は、メッセージを 1 列に並べた形式である。メッセージは次の 3 種類で、どれも「継続マーカー（0xFFFFFFFF）、メタデータ長、Flatbuffers の Message、パディング、本体」の順にカプセル化され、全体が 8 バイトの倍数になる。

| 要素 | 中身 |
| --- | --- |
| Schema | 列の名前と型。本体を持たない。 |
| 辞書バッチ | 辞書エンコードした列の値表。ID と、追加分だけを送る delta の指定を持つ。 |
| レコードバッチ | 同じ行数の各列のバッファ。本体にバッファを並べる。 |

並びは Schema、辞書バッチ、レコードバッチの順で、辞書は参照するレコードバッチより前に定義する。ファイル形式はこの並びの前後に、先頭の `ARROW1` マジックと、末尾のフッター・フッター長・`ARROW1` を付ける。フッターは Schema の複製と、各辞書バッチ・レコードバッチの位置とサイズを持つ。違いの詳細は [ストリーム形式とファイル形式の違い](reference-arrow-ipc-stream-file.md) に分けた。

圧縮は本体のバッファ単位で、なし・lz4（フレーム形式）・zstd から選ぶ。1 つのメッセージ内では同じコーデックを使い、個々のバッファを非圧縮のままにもできる。バイト順は既定でリトルエンディアンである。

## 3. 書き手

書き手は Schema を書き、辞書があれば辞書バッチを書き、レコードバッチを追記する。閉じるときにストリームは終端マーカー（0xFFFFFFFF の後に長さ 0）を書き、ファイル形式はさらにフッターを書く。PyArrow では `pa.ipc.new_file()` がファイル形式、`pa.ipc.new_stream()` がストリーム形式の書き手を作る。API は共通である。

## 4. 読み手

ファイル形式の読み手は末尾のフッターで各ブロックの位置を知り、必要なレコードバッチだけを読める。PyArrow では `pa.ipc.open_file()` の `num_record_batches` と `get_batch(i)` が相当する。入力は seek できる必要がある。メモリマップなど、ゼロコピーで読める入力では、返るバッチは新しいメモリを確保しない。高水準の `read_table()` ではメモリマップでも常駐メモリは減らないと、公式ドキュメントは注意している。

統計や索引による読み飛ばしの仕組みは、この形式の仕様には書かれていない（フッターが持つのはブロックの位置とサイズ）。

## 5. ストレージ

IPC ファイルは通常のファイルとして、ローカルディスクやオブジェクトストレージに置く。推奨の拡張子は、ファイル形式が `.arrow`（MIME は `vnd.apache.arrow.file`）、ストリーム形式が `.arrows` である。Feather V2 は IPC ファイル形式そのもので、PyArrow の Feather 関数は lz4 を既定にする（使える場合）。V1 は別の旧形式で、圧縮を持たず、25.0.0 で非推奨になった。

## 6. シナリオの見方

書き手が Schema と辞書を先に書き、バッチを追記し、閉じるときに終端とフッターを書く。読み手は末尾のフッターから入り、1 バッチだけを読む。

## 7. 実装例 AWS：EC2 上の Python と S3

EC2 上の Python プロセスが PyArrow で S3 に `.arrow` を書き、別のプロセスが `open_file` で読む。公式ドキュメントの API と形式の説明を組み合わせた代表的な構成で、実在の導入事例や検証済みの構成ではない。S3 を `open_file` に渡す具体的な方法（ファイルシステム実装）と、フッター読みで発生する範囲読みの回数は未確認。IAM ロールの権限範囲も前提である。

## 8. 実装例 自前：ローカルディスク

自前のサーバーで Python がローカルの `.arrow` に書き、`pa.memory_map()` で開いて読む。公式ドキュメントに、メモリマップの入力ではバッチが新しいメモリを確保しない例がある。性能の数値は検証していない。
