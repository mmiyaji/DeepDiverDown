# Karapace のスキーマレジストリ

Karapace の公式 README（GitHub: Aiven-Open/karapace）と公式サイトを基準に、構成部品・保存の仕組み・primary の選出・実行場所を整理する。取得日は 2026年11月28日。版ごとの差は確認していない。

## 1. Karapace の位置づけ

Karapace は、Confluent Schema Registry と Kafka REST Proxy の置き換えとして使えるオープンソースの実装である。Python で書かれ、Schema Registry 側は FastAPI、REST Proxy 側は aiohttp を基盤にする。Avro、JSON Schema、Protobuf のスキーマをサブジェクトごとに版管理し、版の間の互換性を検査する。

メッセージ本体の保管やストリーム処理は担わない。Kafka のレコードにはスキーマ ID を載せ、スキーマ本体は Registry から取り出す。

## 2. 入口：Schema Registry API・REST Proxy

- **Schema Registry API**：既定のポートは 8081。API は Confluent Schema Registry 6.1.1 互換を目標にする（正規化やエラーメッセージに差があると README が注記している）。
- **REST Proxy（Kafka REST）**：既定のポートは 8082。HTTP で Kafka にレコードを送受信し、クラスターの管理操作もできる。スキーマの操作では Registry を呼ぶ。
- **プロセスの役割**：`karapace_registry` と `karapace_rest`（どちらも既定は `true`）で、同じプロセスで起動する部品を選ぶ。少なくとも 1 つは有効にする。
- **クライアント**：Confluent 互換のシリアライザーを使う Producer / Consumer が `schema.registry.url` を Karapace に向ける。登録担当は REST で直接スキーマを登録する。

## 3. 情報モデル：サブジェクト・バージョン・スキーマ ID

- サブジェクトごとにスキーマの版の履歴を持ち、各スキーマには ID が付く。API は Confluent 互換なので、用語もそれに従う。
- IMPORT モードでは、ID と版を指定して登録でき、互換性検査と重複排除を行わない。ID は一度結び付けると変更しない。
- `allow_duplicate_schema_ids`（既定 `true`）と `mode_mutability`（既定 `true`）が取り込みの挙動を決める。
- Protobuf だけ正規化に対応する（フィールドの順序、`map<K, V>` の記法の復元）。

## 4. 互換性

- モードは `NONE`、`BACKWARD`、`BACKWARD_TRANSITIVE`、`FORWARD`、`FORWARD_TRANSITIVE`、`FULL`、`FULL_TRANSITIVE`。transitive 付きは過去の全バージョンと、付かないものは最新のバージョンとだけ比べる。
- Registry のモードは `READWRITE`（既定）と `IMPORT`。
- JSON Schema は `$schema` の URI に応じて Draft 04、06、07、2019-09、2020-12 を検証する（既定は Draft-7）。`unevaluatedProperties`、`$dynamicRef`、`$vocabulary` を含むと互換性検査は失敗側に倒れ、サブジェクトを `NONE` にしない限り登録は拒否される。

## 5. ストレージ：Kafka の `_schemas` トピック

- スキーマと設定の変更は、Kafka のトピック（`topic_name`、既定 `_schemas`）に書く。専用のデータベースは使わない。
- 各 Registry インスタンスは、このトピックを読み込んで内部の状態を作り、続けて更新する（schema reader）。API の読み取りはこの状態から返す。
- `replication_factor`（既定 `1`）は、トピックを作るときのレプリカ数。本番での推奨値は README に書かれていない（未確認）。
- `kafka_schema_reader_strict_mode`（既定 `false`）は、トピックに不正なレコードがあるときに停止するかを決める。
- 各インスタンスは、`karapace-autogenerated-` で始まる単独メンバーのコンシューマーグループを使う。接続するユーザーには、そのグループへの Describe と Read が要る。

## 6. primary と replica

- 構成は Leader/Replica と説明される。書き込み（登録・設定変更）は primary（README の表記は master）が担当する。replica からの書き込みの扱いの細部は README に書かれていない（未確認）。
- 選出は Kafka のグループ（`group_id`、既定 `schema-registry`）を使う。`master_election_strategy`（既定 `lowest`）では、資格のあるインスタンスのうち `client_id` が辞書順で先頭のものが選ばれる。
- `master_eligibility`（既定 `true`）を `false` にすると、そのインスタンスは primary にならない（待機の役）。
- `waiting_time_before_acting_as_master_ms`（既定 5000）は、新しい primary が動き出すまでの待ち時間。低すぎると高負荷時に ID が重複するおそれがあると README が警告している。
- インスタンス同士が互いに到達するため、`advertised_hostname`、`advertised_port`、`advertised_protocol` を設定する。

## 7. 認証・認可

- **Schema Registry**：HTTP Basic（`registry_authfile` のユーザーと権限。`karapace_mkpasswd` で作る）と、OAuth2/OIDC の Bearer トークン（JWKS で検証）。認可は `Config:` と `Subject:<正規表現>` に対する Read / Write で書く。
- **REST Proxy**：`rest_authorization` を `true` にすると、クライアントの Bearer トークンを SASL OAUTHBEARER で Kafka に渡し、認可を Kafka に任せる。
- `/docs`、`/redoc`、`/openapi.json` は認証をかけないので、本番では逆プロキシで止めるよう README が助言している。
- TLS は `server_tls_*` で設定する。

## 8. 動く場所と運用

- イメージは `ghcr.io/aiven-open/karapace`（`latest` と `develop`）。設定は環境変数 `KARAPACE_<キー名の大文字>` で上書きできる。
- メトリクスと OpenTelemetry に対応し、Sentry も任意で使える。
- 公式サイトは、マネージドの提供事業者でも自前でも動かせるとしている。具体的なマネージド版の構成は確認していない。
- ライセンスは Apache License 2.0（README）。CLA は不要と書かれている。

## 9. 実装例：オンプレミスの VM・Kafka クラスター

利用者のデータセンターに、Kafka クラスターと、Karapace を動かす VM を複数置く例。全インスタンスが同じ `group_id` と `topic_name` を使い、前段のロードバランサーが 8081 を振り分ける。

| 機能 | 担い手 |
| --- | --- |
| 登録担当・クライアント | データセンター外のアプリ |
| Schema Registry API・互換性・情報モデル・schema reader | Karapace の primary と replica の VM |
| 選出 | Kafka のグループ |
| ストレージ | Kafka クラスターの `_schemas` トピック |
| 実装で加わる部品 | ロードバランサー |

台数、VM の大きさ、REST Proxy を同じ VM に置くかは資料で指定されていない。公式資料を組み合わせた代表例で、実環境での動作は未検証である。
