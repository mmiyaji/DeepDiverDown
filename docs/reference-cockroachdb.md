# CockroachDB の概要（分散 SQL・トランザクション・レンジ複製・Pebble）

2026 年 11 月時点の公式資料に基づく。資料は docs.cockroachlabs.com の stable 版で、版番号は資料中に明記がなく未確認。

## 1. 概要と層構成

CockroachDB は SQL を受け付け、キーと値（KV）の操作に変換して複数ノードに分散保存するデータベースである。公式資料は 5 層で説明する。SQL 層（SQL を KV 操作に変換）、トランザクション層（複数の KV を原子的に変更）、分散層（複製したレンジを 1 つの KV 空間として見せる）、複製層（レンジを同期的に複製）、ストレージ層（ディスクの読み書き）である。どのノードも SQL を受け付け、自分で処理できない要求は担当ノードへ転送する。PostgreSQL 互換の接続方式、DistSQL による分散実行は、取得した資料に記載がなく未確認。

- [Architecture overview](https://docs.cockroachlabs.com/docs/stable/architecture/overview)

## 2. トランザクション

既定の分離レベルは `SERIALIZABLE`。`READ COMMITTED` も選べ、異常の一部を許す代わりにアボートとクライアント側の再試行が減り、文単位で自動再試行される。書き込みは書き込みインテント（値の仮書き込み兼、複製される排他ロック）として Raft で複製される。インテントはトランザクションレコード（`PENDING`・`STAGING`・`COMMITTED`・`ABORTED`）を指し、コミット後に通常の MVCC 値へ変わる。並列コミットは、`STAGING` のレコードを作って実行中の書き込みの合意を待たずに進め、合意の往復を 2 回から 1 回に減らす。タイムスタンプはハイブリッド論理クロック（HLC）で、ゲートウェイノードがトランザクションごとに選ぶ。クロックのずれが設定の上限を超えると、単一キーの線形化可能性が崩れうる。ノードは、半数以上のノードに対して最大オフセットの 80% を超えてずれると停止する。

- [Transaction layer](https://docs.cockroachlabs.com/docs/stable/architecture/transaction-layer)

## 3. レンジと Raft 複製

キー空間はソート済みの連続区間であるレンジに分かれ、既定で 3 つのレプリカを持つ。レンジの分割サイズ、メタレンジによるキーからレンジの検索は取得した資料に記載がなく未確認。レンジごとに Raft グループがあり、リーダー 1 つとフォロワーからなる。書き込みは過半数の合意でコミットされ、Raft ログが正となる。リースホルダーがレンジの読み取りと書き込みの提案を担当し、リーダーリースでは Raft リーダーと同じレプリカになる（リース移転中を除く）。リースホルダーは Raft を通さず一貫性のある読み取りを返す。リースホルダーのノードが落ちると、新しいリーダーの選出とリース移転が要求時に行われ、数秒かかる。複製係数は、クラスタ・データベース・テーブルの単位で複製ゾーンにより設定する。許容できる障害数は（係数 − 1）/ 2 である。リースホルダーは、クローズドタイムスタンプ以前の書き込みを受け付けないとフォロワーへ約束する。フォロワーは、そのタイムスタンプ以前の読み取りを返せる（フォロワーリード）。クローズドタイムスタンプは通常、現在時刻に対して数秒遅れる。生存目標（survival goal）の具体的な設定は未確認。

- [Replication layer](https://docs.cockroachlabs.com/docs/stable/architecture/replication-layer)

## 4. ストレージ（Pebble）

各ノードには 1 つ以上のストアがある。ストアは、Go で書かれた組み込み KV の Pebble（LSM ツリー、RocksDB に着想）で、一時的な分散 SQL 用と、それ以外のデータ用の 2 つのインスタンスを持つ。メムテーブルごとに WAL が 1 つあり、書き込みは WAL とメムテーブルに同時に入る。SST は L0〜L6 に並び、コンパクションが下へ統合する。値は MVCC のバージョンで保存され、HLC のタイムスタンプで区別される。古い値は `gc.ttlseconds` を過ぎるとガベージコレクションされ、バックアップと変更フィードが必要とするデータは保護タイムスタンプで残る。同じレンジの 2 つのレプリカが同じノードやストアに置かれることはない。

- [Storage layer](https://docs.cockroachlabs.com/docs/stable/architecture/storage-layer)

## 6. 実装例：自前のサーバーでのクラスタ

| 機能 | 具体的な担い手 |
| --- | --- |
| クライアント | SQL クライアント（`cockroach sql` など） |
| 入口の分散 | HAProxy（`cockroach gen haproxy` が生成、TCP モード、ポート 26257） |
| SQL・トランザクション・HLC・レンジ・リース・クローズドタイムスタンプ | `cockroach` プロセス（ノード） |
| Raft フォロワー | 別ノードのレプリカ |
| 保存 | 各ノードのローカルディスクの Pebble ストア |

利用者が自前のマシンで `cockroach start`（`--join` に 3〜5 台を指定）、`cockroach init`、証明書（`cockroach cert`）、NTP を運用する構成。ポートは 26257（ノード間とクライアント）と 8080（DB Console）、ノードはマシンごとに 1 つ。資料は 3 ノードで 1 台の障害に耐え、AZ・リージョンの障害には各 3 つ以上を勧める。公式資料に基づく代表例であり、導入事例や動作検証済みの構成ではない。図は 2 ノードに省略している。実運用の台数、`--locality` の設計、証明書の更新は未確認。
