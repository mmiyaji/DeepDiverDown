# リファレンスの整理の型（分野 → 分類 → 製品 → 図）

サイドバーと分類ページは、リファレンスを次の階層で見せる。新しく作る・作り直すリファレンスはこの型に合わせる。

```
分野（domain）        例：データ処理
└ 分類（category）     例：バッチ・SQL エンジン      ← 分類ページで製品の概要と違いを並べる
  └ 製品（product）    例：Trino                    ← 1 つの製品・OSS・サービス
    ├ 概要（overview）  基本アーキテクチャの図 1 つ
    └ 仕組み（internals） 内部の仕組みを学ぶ順に 1, 2, 3 …
```

製品に当たらない、考え方・設計パターン・トレンドの図は、分類の下の「仕組みとパターン」に置く。

## registry.json の書き方

```json
{
  "id": "trino-query-execution",
  "name": "Trino：Stage・Task・Split と Exchange",
  "actual": false,
  "reference": {
    "domain": "データ処理",
    "category": "バッチ・SQL エンジン",
    "kind": "仕組みの深掘り",
    "product": "Trino",
    "role": "internals",
    "step": 1,
    "detailOf": "trino",
    "also": ["データ配置と読み取り"]
  },
  "tags": ["OSS", "Trino Software Foundation"]
}
```

| 項目 | 意味 |
| --- | --- |
| `product` | 製品名。同じ製品の図はすべて同じ名前にする（例：`Apache Spark`）。考え方・パターンの図には書かない |
| `role` | `overview`（製品の概要、製品ごとに 1 つ）／ `internals`（仕組みの深掘り）／ `concept`（製品に属さない考え方・パターン） |
| `step` | `internals` の学ぶ順序（1 から）。前の図を読んでいる前提で次を読める順にする |
| `detailOf` | `internals` は同じ製品の `overview` を指す。**別の製品や概念の図を親にしない** |
| `category` | その図の中身にいちばん合う分類を 1 つ |
| `also` | 製品として載せたい、ほかの分類（任意。同じ分野の分類だけ） |
| `kind` | 既存の表示用。`overview` は「製品・技術のアーキテクチャ」、`internals` は「仕組みの深掘り」、`concept` は内容に合わせる |

## 図の作り方の約束

- **1 つの図は 1 つの製品だけを扱う。** 複数の製品を比べる内容は、図ではなく分類ページの「違い」に書く。
- **概要の図**は、その製品を初めて学ぶ人向けに、主要な部品・データの流れ・実行場所を示す。名前は「<製品名> の基本アーキテクチャ」。
- **仕組みの図**は 1 つの論点に絞る（例：実行計画、メモリと spill、ストレージ形式）。名前は「<製品名>：<論点>」。
- ID は製品名を先頭に付ける（`trino`、`trino-query-execution`）。
- モデルの書き方・根拠・実装例・検証は [モデル作成ルール](../AGENTS.md) と [モデル仕様](model-schema.md) に従う。解説は `docs/reference-<id>.md`。

## 分類ページの「違い」

分類ごとに `docs/category-<slug>.md` を置き、その分類の製品を同じ観点で比べる表を書く。観点は分類ごとに決める（バッチ・SQL エンジンなら、実行モデル・スケール・ストレージとの関係・得意な処理・運用形態）。

## 実装例の稼働環境

すべての実装例は、利用者・外部クライアント以外の部品を稼働環境の枠（クラウドは `kind: cloud` と `provider`、自前の拠点や手元の PC は `kind: datacenter` と `provider: onprem`）に入れる。2D・3D の表示用の `groups` にも同じ枠を置く。`node tools/audit-provider-boundaries.mjs <id>` で点検し、`product` を書いたリファレンスはテストでも確かめる。

## 仕組みの図にも実装例を付ける

`overview` だけでなく `internals` にも、現実的な実装例（`implementations`）を 1 つ以上付ける。概要と同じ稼働環境の例でよい。部品の役割は `realizes` で対応付け、根拠の公式資料を `sources` に書く（`tests/references.test.mjs` で確かめる）。

## 分類ページの比較表の書き方

`docs/category-<slug>.md` に置き、`js/categories.js` の `CATEGORY_DOCS` に分類名と slug を登録する。

- 1 行目は **特徴**：その製品の持ち味を 1 句で（例：「**集計の速さ** に特化」）。製品全体の説明は書かない。
- 2 行目以降は分類ごとの観点。観点の名前は読み手の疑問に近い言葉にする（「ストレージとの関係」より「データの置き場所」、「運用形態」より「動かし方」）。
- セルは文にせず、要点の句にする。1 セル 1〜2 句、30 字前後まで。
- 各セルで、ほかの製品との違いになる 1〜2 語だけを `**太字**` にする（画面では強調表示になる）。全部を太字にしない。
- 表の下に「選び方」を置き、「具体的な場面 → **製品名**」の形で書く（例：「ダッシュボードから同じ表へ何度も集計を投げる → **ClickHouse**」）。
- 最後に「公式資料」のリンク。
- 前置き文は書かない。題名（`# …の違い`）のすぐ下に表を置く。

## 文章の書き方（AI っぽい文を避ける）

図の名前・説明・解説・比較表のすべてで次を守る。

- 中身のない前置き・まとめを書かない（「〜は大きく異なります」「〜を理解することが重要です」「このように〜」）。
- 抽象語で言い換えない。具体的な部品名・設定名・場面で書く（「柔軟に」「効率的に」「シームレスに」「強力な」を使わない）。
- 同じ型の文を並べない。体言止めと「〜し、〜する」の連続、3 つ並べの列挙の多用を避ける。
- 根拠のない数値や断定を書かない。確かめていないことは `unknowns` と解説に「未確認」と書く。
- 文末は「です・ます」か「である」をファイル内でそろえる。

## 作業の進め方（複数製品を作り直すとき）

1. 分類内の製品を決め、製品ごとに作業者（安いモデルの Sonnet など）へ分担する。1 人 1 製品。`models/registry.json`・`js/`・`css/` は作業者に触らせず、登録したい内容は JSON で受け取る。
2. 作業者は概要 1 つと仕組み 2〜4 つを作る。既存の図は、型に合えば ID を変えて仕組みに移し、合わなければ捨ててよい。
3. 取りまとめ役が registry に反映し、`node tools/build-index.mjs` を実行する。
4. 完了条件：
   - `node tools/gates.mjs <id>`：台数の警告（HIGH_ISSUES）以外は合格
   - `node tools/audit-provider-boundaries.mjs <id>`：問題なし
   - `npm test`：すべて合格
   - 分類ページで、製品カード・縮小図・比較表・学ぶ順序の番号を確かめる
5. 比較表は、作業者の報告（製品ごとの観点メモ）をもとに取りまとめ役が書く。
