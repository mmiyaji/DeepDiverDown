# リファレンスの整理の型（分野 → 分類 → 製品 → 図）

サイドバーと分類ページは、リファレンスを次の階層で見せる。新しく作る・作り直すリファレンスはこの型に合わせる。

```
分野（domain）        例：データ処理
└ 分類（category）     例：バッチ・SQL エンジン      ← 分類ページで製品の概要と違いを並べる
  └ 製品（product）    例：Trino                    ← 1 つの製品・OSS・サービス
    ├ 概要（overview）  基本アーキテクチャの図 1 つ
    └ 仕組み（internals） 内部の仕組みを学ぶ順に 1, 2, 3 …
```

製品に当たらない、考え方・設計パターン・トレンドの図は、分類の下の「仕組みとパターン」に置く。

## registry.json の書き方

```json
{
  "id": "trino-query-execution",
  "name": "Trino：Stage・Task・Split と Exchange",
  "actual": false,
  "reference": {
    "domain": "データ処理",
    "category": "バッチ・SQL エンジン",
    "kind": "仕組みの深掘り",
    "product": "Trino",
    "role": "internals",
    "step": 1,
    "detailOf": "trino",
    "also": ["データ配置と読み取り"]
  },
  "tags": ["OSS", "Trino Software Foundation"]
}
```

| 項目 | 意味 |
| --- | --- |
| `product` | 製品名。同じ製品の図はすべて同じ名前にする（例：`Apache Spark`）。考え方・パターンの図には書かない |
| `role` | `overview`（製品の概要、製品ごとに 1 つ）／ `internals`（仕組みの深掘り）／ `concept`（製品に属さない考え方・パターン） |
| `step` | `internals` の学ぶ順序（1 から）。前の図を読んでいる前提で次を読める順にする |
| `detailOf` | `internals` は同じ製品の `overview` を指す。**別の製品や概念の図を親にしない** |
| `category` | その図の中身にいちばん合う分類を 1 つ |
| `also` | 製品として載せたい、ほかの分類（任意。同じ分野の分類だけ） |
| `kind` | 既存の表示用。`overview` は「製品・技術のアーキテクチャ」、`internals` は「仕組みの深掘り」、`concept` は内容に合わせる |

## 図の作り方の約束

- **1 つの図は 1 つの製品だけを扱う。** 複数の製品を比べる内容は、図ではなく分類ページの「違い」に書く。
- **概要の図**は、その製品を初めて学ぶ人向けに、主要な部品・データの流れ・実行場所を示す。名前は「<製品名> の基本アーキテクチャ」。
- **仕組みの図**は 1 つの論点に絞る（例：実行計画、メモリと spill、ストレージ形式）。名前は「<製品名>：<論点>」。
- ID は製品名を先頭に付ける（`trino`、`trino-query-execution`）。
- モデルの書き方・根拠・実装例・検証は [モデル作成ルール](../AGENTS.md) と [モデル仕様](model-schema.md) に従う。解説は `docs/reference-<id>.md`。

## 分類ページの「違い」

分類ごとに `docs/category-<slug>.md` を置き、その分類の製品を同じ観点で比べる表を書く。観点は分類ごとに決める（バッチ・SQL エンジンなら、実行モデル・スケール・ストレージとの関係・得意な処理・運用形態）。
