# Memcached の分散キャッシュ

## 1. 概要

Memcached はメモリ上にキーと値を置く分散キャッシュである。アプリケーションは先に Memcached を調べ、なければデータベースへ問い合わせる。Memcached が落ちても、その分のリクエストがミスになるだけで、ほかのインスタンスは動き続ける。2026 年 11 月時点の公式資料に基づく。

[Memcached ドキュメント: 用途の例（Caching Story）](https://docs.memcached.org/tutorialcachingstory/)

## 2. クライアント側の分散とサーバーの独立

各 Memcached サーバーは互いに通信せず、メモリ上限も個別に持つ。クライアントは起動時にサーバーのリストからハッシュ表を作り、キーごとに 1 台を選ぶ。1 つのキーは 1 台にだけ置かれる。ハッシュ方式の名称（一貫性ハッシュなど）は今回取得した資料に記載がなく未確認。既定のポート 11211 も、取得範囲では既定値として明記されておらず未確認。

[Performance and Efficiency](https://docs.memcached.org/serverguide/performance/)

## 3. スレッドとハッシュ表

接続を受け付けるスレッドが 1 つあり、ワーカースレッドはそれぞれ libevent のイベントループで自分のクライアントを処理する。スレッド間では集中ロックでキャッシュを共有する。キーの検索にはハッシュ表を使い、そのメモリは `-m` の上限の外で消費される。

## 4. スラブアロケータ

`-m` で指定したメモリは、既定で 1 MB のページに分けられる。ページはスラブクラスに割り当てられ、固定サイズのチャンクに切られる。アイテムは大きさが最も近いクラスに入る。一度割り当てたページは別のクラスへ移らない。クラス 1 のチャンクは 80 バイトで、`-f` で調整できる。スラブのリバランス機能は、取得範囲に記載がなく未確認。

## 5. LRU と追い出し

LRU はスラブクラスごとにある。空きチャンクがないとき、LRU の末尾から期限切れのアイテムを探して再利用し、なければ期限内のアイテムを追い出す。

`-o lru_maintainer` を指定すると、LRU は HOT・WARM・COLD の区画に分かれる。新しいアイテムは HOT に入り、2 回以上読まれたアイテムは活動中として扱われる。活動中の HOT は WARM へ移り、COLD で読まれたアイテムは WARM へ戻る。HOT と WARM はスラブクラスのメモリに対する割合に上限があり、COLD に上限はない。`-o temporary_ttl=N` を指定すると、TTL が N 以下のアイテムは TEMP に入り、追い出されない。LRU メンテナースレッドが区画間の移動を非同期に行い、LRU クローラーが期限切れアイテムを回収する。区画の割合の既定値と、この機能が現行版で既定で有効かどうかは未確認。

[new_lru.txt](https://github.com/memcached/memcached/blob/master/doc/new_lru.txt)

## 6. 永続化なし、ウォームリスタート

通常の Memcached は値をメモリにだけ持ち、再起動で消える。`-e` で RAM ディスク上のファイルを指定すると（1.5.18 以降）、SIGUSR1 による正常終了後にキャッシュを引き継げる。値は mmap ファイルに入り、ハッシュ表は再起動時に作り直す。`-m` やスラブのチャンクサイズを変えると、キャッシュは空で始まる。停止中の更新は失われる。公式資料は、永続メモリ（DAX）を使っても crash safe にはならないと明記している。ウォームリスタートは extstore と併用できない。

[Warm Restart](https://docs.memcached.org/features/restart/)

## 7. extstore による外部ストレージ

extstore（1.6.0 以降）は、LRU の末尾にある値をフラッシュ媒体へ書き出す。ハッシュ表、キー、メタデータ、フラッシュ上の位置を示す約 12 バイトのヘッダーは RAM に残る。値は RAM の書き込みバッファにためてから、固定サイズのページ（既定 64 MB）へ順に書く。短い間に何度も読まれた値は、一定の確率で RAM に戻される。`-o ext_path=/path/to/file:SIZE` で有効にする。回転ディスクは使えない。フラッシュ済みアイテムでは incr/decr、append、prepend が使えず、UDP も使えない。位置の索引が RAM にだけあるため、再起動でフラッシュの内容は使えなくなる。

[Extstore](https://docs.memcached.org/features/flashstorage/)

## 8. 実装例：自前の 2 台構成

Memcached サーバーを自前のホスト 2 台で動かし、アプリケーションのクライアントライブラリがキーごとに 1 台を選ぶ例である。代表例であり、導入事例ではない。

| 機能配置の役割 | 実装の担い手 |
| --- | --- |
| アプリケーション、クライアントのハッシュ表 | アプリケーション（クライアントライブラリを含む） |
| データベース | 利用者のデータベース |
| Memcached サーバー A、ワーカースレッド、ハッシュ表、スラブクラス、LRU | 自前ホスト上の Memcached プロセス 1 つ |
| Memcached サーバー B | 別ホスト上の Memcached プロセス |
| extstore | 任意のローカルフラッシュ（有効化は未確認） |

根拠は [Performance and Efficiency](https://docs.memcached.org/serverguide/performance/) と [Caching Story](https://docs.memcached.org/tutorialcachingstory/)。ホストの構成、クライアントと Memcached 間の接続方式、extstore の有無は資料にないため未確認。
