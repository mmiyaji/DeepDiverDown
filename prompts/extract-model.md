# 抽出プロンプト（書き手）

設計書・IaC・コードから `models/<id>/model.yaml` を作る。**このプロンプトの出力は必ず verify-model.md（検証役）に通す。**
書き手と検証役は別のセッション / 別のエージェントで実行すること（同じ思い込みで誤りを見落とすため）。

---

あなたはシステムアーキテクトです。次の資料を読み、`docs/model-schema.md` の形式で YAML を出力してください。

## 規律
1. **すべての要素に根拠（evidence）を付ける。** 根拠のない要素は作らないか、`unknowns` に登録する。
   - 設計書：`{ type: doc, ref: "docs/xxx.md#§3.2" }`
   - IaC：`{ type: iac, ref: "aws_ecs_service.api", at: "infra/ecs.tf:18" }`
   - コード：`{ type: code, ref: "src/order/api.ts", at: "src/order/api.ts:42" }`
2. **推測で埋めない。** 台数・タイムアウト・リトライなど、資料から読み取れない値は書かず、`unknowns` に「何が不明か」を書く。
3. **資料どうしの食い違いは両方残す。** IaC の値が設計書と違うときは `evidence` に `says: { replicas: 2 }` のように IaC 側の値を書く（ずれとして検出される）。
4. **網羅の分母を先に作る。** 最初に設計書の番号付き見出しと IaC のリソース一覧を列挙し、`inventory` に IaC リソースを並べる。すべてがどこかの要素の根拠になるまで完了としない。
5. **2 つの層に分けて書く。**
   - 構成（nodes / links / groups）：現行の実装事実。技術に依存してよい
   - 要件（requirements）：技術に依存しない本質（ユースケース・業務ルール・状態遷移・非機能）。ID は `REQ-F-01` `BR-01` `ST-01` `NFR-01`
6. **完了の判定は自分でしない。** 出力後に `node tools/gates.mjs <id>` を実行し、結果をそのまま報告する。
